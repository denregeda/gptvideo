## Компоненты

### Сервер (Docker Compose, 7 контейнеров)
| Контейнер | Роль |
|---|---|
| **ds_nginx** | Точка входа :80. Отдаёт веб-панель (статика), проксирует API и WebSocket, раздаёт медиафайлы мини-ПК. Единственный HTTP-порт наружу. |
| **ds_api** | FastAPI-приложение. Вся бизнес-логика: экраны, медиа, плейлисты, расписание, кампании, биллинг, модерация, пользователи, OTA. 17 роутеров в `server/routers/`. |
| **ds_postgres** | PostgreSQL 15. Все данные системы. Схема разворачивается миграциями `001`–`032` при первом старте. |
| **ds_redis** | Брокер и хранилище результатов для Celery. |
| **ds_celery** | Worker + Beat (флаг `-B`). Фоновые задачи: ночные бэкапы БД, бэкап медиа в MinIO, архивирование `play_log`, уведомления (MAX), пересчёт KPI. |
| **ds_minio** | S3-совместимое хранилище резервных копий медиа. |
| **ds_ntp** | chrony. Раздаёт точное время мини-ПК (udp/123), сам синхронизируется с ВНИИФТРИ/MSK-IX при наличии интернета. |

### Мини-ПК (агент, Astra Linux)
systemd-сервис `ds-agent` (Python). Модули: `ds_agent` (главный),
`ds_downloader` (координация файлов), `ds_media_transfer` (атомарная загрузка,
resume и проверка), `ds_player` (плеер + IPC-сокет),
`ds_sync` (синхронизация), `ds_heartbeat` (мониторинг), `ds_cleanup`
(очистка), `ds_ws_client` (WebSocket-команды), `ds_ota_updater` (самообновление).

## Потоки данных

**Публикация контента (оператор → экран):**
1. Оператор загружает ролик в панель → `api` кладёт файл в том `media_data`,
   запись в Postgres, статус модерации `pending`.
2. Модератор одобряет (38-ФЗ) → статус `approved`.
3. Оператор ставит ролик в плейлист и в расписание.
4. Агент опрашивает `api` (poll_interval 60 c), получает своё расписание,
   **скачивает** нужные файлы через nginx `/media/` в скрытый `.part`
   (с докачкой по Range).
5. Плеер проигрывает по времени; синхронный старт по `sync_delay`.

Рабочий медиафайл не меняется во время передачи. Агент проверяет
`Content-Range`, точный размер и MD5 временного файла, вызывает `fsync` и лишь
затем публикует его через атомарный `rename`. Обрыв связи оставляет старый
ролик пригодным для эфира, а `.part` — для следующей докачки.
Серверный `file_delivery.py` возвращает `206 Partial Content` и точный
`Content-Range`; неподдерживаемый или выходящий за размер диапазон получает
`416`, поэтому агент не может незаметно склеить несовместимые части.

Если файловый манифест недоступен из-за сети, HTTP-ошибки или некорректного
JSON, агент пропускает синхронизацию и очистку. Ошибка не трактуется как
успешный пустой список: уже скачанные ролики сохраняются для офлайн-эфира.

**Команды в реальном времени (панель → экран):**
`api` пушит команду (перезапуск/перезагрузка) в `ds_ws_client` агента по
WebSocket (`/ws/`, `/api/ws/*`) — доставка мгновенная, без ожидания опроса.
Токен устройства передаётся в заголовке handshake `X-Token`, а JWT панели —
через пару WebSocket subprotocol `ds-auth,<JWT>`. Секреты в query string
запрещены: nginx удаляет параметры запроса перед проксированием WebSocket и
пишет access-лог без query string.

**Мониторинг (экран → сервер):**
Агент шлёт heartbeat каждые ~30 c → `api` обновляет статус онлайн/офлайн,
свободное место, версию, играющий контент → видно на Дашборде.

**Точное время:** мини-ПК синхронизируются с `ds_ntp` (в изолированной сети —
единственный источник). Критично: расписание и учёт показов считаются по
московскому времени.

## Хранилище (Docker-тома)
| Том | Что хранит |
|---|---|
| `postgres_data` | База данных (все записи системы) |
| `media_data` | Загруженные медиафайлы (шарится: `api`, `celery` — rw; `nginx` — ro) |
| `minio_data` | Резервные копии медиа (S3) |
| `backup_data` | Ночные дампы БД |
| `agent_updates_data` | Пакеты OTA-обновления агентов |
| `nginx_logs` | Логи nginx |

> Тома переживают пересборку контейнеров. `docker compose down -v` их **удаляет**
> — только после бэкапа.

## Миграции БД
SQL-файлы `server/migrations/001`–`032`, применяются Postgres автоматически при
первом старте (список смонтирован в `docker-entrypoint-initdb.d` в
`docker-compose.yml`). На уже работающей БД недостающие миграции добивает
`migrate.sh` (вызывается из `install_server.sh` при обновлении).

> На момент актуальны `001`–`032` (026 — авто-снятие бегущей строки, 027 —
> архивы диагностики экранов, 028 — контроль подключения монитора к
> видеовыходу, 029 — раздел «Рекламодатели»: реквизиты, договоры, документы,
> компенсации, заявки, 030 — госорганы как владельцы контента без
> биллинга, 031 — индивидуальные финансовые условия кампаний, 032 —
> восстановление стандартных папок рекламодателей). Новые миграции достаточно
> положить в `server/migrations/` — `migrate.sh`
> применит их идемпотентно; в `docker-compose.yml` их добавляют для применения на
> ЧИСТОЙ установке через initdb.

## Индивидуальные условия кампании

Кампания хранит собственный снимок финансовых условий:

- `billing_mode`: только `per_play` или `per_minute`;
- `unit_price`: цена одного показа или минуты;
- `discount_amount`: ручная скидка администратора;
- `discount_note`: обязательное основание скидки;
- автор и время последнего изменения условий.

Денежная математика вынесена в `server/billing/campaign_pricing.py` и использует
`Decimal`. Шаблон рекламодателя служит значением по умолчанию только при
создании кампании. Его последующее изменение не переписывает кампанию.
Рекламодатель видит условия и расчёт, но изменять их не может.
Интерфейс заявок вынесен в отдельный модуль
`server/static/js/views/advertiser_requests.js`, чтобы развитие кабинета не
увеличивало основной файл карточки рекламодателя.
Формы редактирования условий и имени также вынесены в
`campaign_pricing.js` и `advertiser_identity.js`; общий каркас модальных окон
находится в `core/modal.js`.

Две стандартные папки владельца (`Видеореклама`, `Документы`) создаются
идемпотентно. Миграция 032 восстанавливает их у старых записей, а чтение списка
владельцев выполняет лёгкую самопроверку. API запрещает удалять эти две папки.

## Роль «рекламодатель»: два независимых рубежа
Учётка с ролью `advertiser` привязана к записи рекламодателя
(`users.advertiser_id`, заводится автоматически при создании пользователя).
Ограничение доступа сделано **на сервере в двух местах**, потому что скрытие
пунктов меню в панели защитой не является — API можно позвать напрямую:

1. **Middleware `advertiser_guard`** (`server/main.py`) — белый список путей
   (`deps._ADV_ALLOWED`), всё остальное 403. Принцип «запрещено по умолчанию»:
   один забытый эндпоинт не превращается в утечку чужого эфира и счетов.
2. **Зависимость `advertiser_scope`** (`server/deps.py`) — id кабинета в пути
   обязан совпадать с привязкой учётки, иначе 403. Перебором номеров чужую
   карточку не открыть.

WebSocket-соединения middleware не проходят, поэтому дашборд-поток
(`/ws/dashboard`) отсекает эту роль отдельной проверкой в
`routers/websockets.py`. Изоляция закреплена E2E-прогоном (`ui_test.sh`).

## Границы безопасности
- Наружу открыты только **:80** (nginx) и **:123/udp** (ntp).
- Postgres, Redis, MinIO, API **не** имеют проброса портов на хост — доступны
  только внутри сети Docker.
- Агенты аутентифицируются токеном устройства (заголовок `X-Token`).
- WebSocket не принимает токены из URL: агент использует `X-Token`, панель —
  защищённый subprotocol handshake. Сервер подтверждает браузеру только
  публичный протокол `ds-auth`, не отражая JWT в ответе.
- Пользователи панели — по логину/паролю, токен входа подписан `SECRET_KEY`.
- Текущая роль, блокировка и существование пользователя подтверждаются в
  PostgreSQL на каждом HTTP/WebSocket-подключении через `auth_identity.py`.
  При ошибке БД сервер отвечает `503` (WebSocket: `1013`) и **никогда** не
  подставляет аварийную роль. Удаление, блокировка или смена роли действуют
  сразу и для ранее выданного JWT. Запись и модерация разрешаются только
  явным белым спискам ролей.
- Полные дампы PostgreSQL доступны только ролям `admin` и `superadmin`
  (`require_backup_admin`). Список, создание, скачивание и удаление закрыты
  на API; скачивание/удаление пишутся в аудит, путь файла проверяется внутри
  `BACKUP_DIR`. Панель передаёт токен при скачивании через `fetch`.
- Секреты (`DB_PASSWORD`, `MINIO_PASSWORD`, `SECRET_KEY`) — в `.env` (права 600,
  в git не попадает).
- При первом входе панель **принудительно требует сменить** пароль admin по
  умолчанию (флаг `must_change_password`).

### Транспорт: HTTP без TLS — осознанное решение
Система работает по **HTTP** (без шифрования). Это принятое решение для
**изолированной indoor-сети**: сервер и мини-ПК в одном закрытом сегменте LAN,
наружу проброшены только порты 80 и 123/udp, внешнего доступа нет. В такой
конфигурации риск перехвата трафика низкий, и HTTP приемлем.

> **Когда включать HTTPS/TLS:** если панель/API станут доступны из внешней сети
> (интернет, общий Wi-Fi, доступ подрядчиков). Тогда логин и токены нельзя
> передавать в открытом виде. Шаги: сертификат (самоподписанный для внутренней
> сети или Let's Encrypt для публичного домена) → в `nginx.conf` добавить
> `listen 443 ssl` + редирект с 80 → пробросить 443 в `docker-compose.yml` →
> переустановить агенты с `https://…` (install.sh уже поддерживает https) →
> доверить сертификат на мини-ПК. Обязательна проверка на железе.
